# برنامهٔ پیشنهادی بستهٔ پیش‌نمایش محافظت‌شده

**وضعیت: بستهٔ آزمایشی production در دست آزمون؛ هنوز برای استقرار VPS تأیید نشده و مستقر نشده است.** مالک مقصد `https://preview.xennic.ir` را برای پیش‌نمایش محافظت‌شده تأیید کرده است؛ در این مرحله هیچ اقدامی روی VPS یا DNS مجاز نیست. انتخاب نهایی با پاسخ دستیار زیرساخت و تأیید تصمیم‌های اثرگذار انجام می‌شود. این سند جایگزین Vault نیست.

## مبنا و مرزها

- کد وب‌سایت: `dev` در `068cab5ea1f02e60a236094b3b7c43a49431f462`، پس از [PR شمارهٔ ۶](https://github.com/feerozmandi/xennic-website/pull/6).
- مرجع Vault فقط‌خواندنی: شاخهٔ `dev` در `c51e087f206b235987987906c62ea4a0ed689967`: `L2-MKT-005` v0.4.0 §§۲–۶، `META-INT-150` v0.3.0 §§۳–۵، `META-INT-140` v0.6.0 §§۲، ۷ و ۸، `META-INT-100` v0.3.0، `META-INT-110` v0.4.2 و `META-INT-130` v0.2.2. وضعیت VPS در این اسناد تاریخی است و در این نشست راستی‌آزمایی زنده نشده است.
- Payload در Next.js تعبیه شده، PostgreSQL وب‌سایت/پلتفرم آینده از نمونهٔ n8n جدا است، و `website` و `shared.customers` مطابق معماری موجود می‌مانند. پیش‌نمایش باید علاوه بر این، از **هر پایگاه‌داده و فایل عملیاتی وب‌سایت** نیز جدا باشد. جداسازی محیط پیش‌نمایش به‌معنای تغییر تصمیم Modular Monolith در هر محیط نیست.
- فازهای زیرساخت `۰/A` و وضعیت واقعی Caddy/TLS و محدودیت‌های دسترسی باید از دستیار زیرساخت تأیید شوند. مجوز مقصد پیش‌نمایش به‌تنهایی اثبات آمادگی یا اجازهٔ اجرای فعلی روی سرور نیست.
- فرم، اتصال n8n/CRM، تحلیل‌گر، خرید فونت و انتشار عمومی خارج از محدوده‌اند. هیچ دادهٔ واقعی مشتری یا محتوای عملیاتی نباید به محیط آزمایش کپی شود.

## طرح فنی برای بررسی، نه نسخهٔ نهایی

1. **اثر قابل‌تکرار:** ایمیج نسخه‌گذاری‌شدهٔ Next.js/Payload با نصب وابستگی پین‌شده، `npm run build` در مرحلهٔ build و `npm run start` در زمان اجرا؛ پیشنهاد Docker Compose مستقل با سرویس برنامه و PostgreSQL 16 مستقل. ساخت ایمیج ترجیحاً خارج VPS انجام شود تا build و cache، منابع پشتهٔ عملیاتی را مصرف نکنند؛ مسیر انتقال یا registry و سازگاری معماری CPU نیاز به تأیید دارد.
2. **ایزوله‌سازی:** project name، سرویس‌ها، شبکه، PostgreSQL، credential، volume دیتابیس و volume آپلود جدا و مختص staging باشند؛ نام‌ها پس از دریافت inventory انتخاب و عدم برخورد بررسی شود. PostgreSQL هیچ پورت عمومی نداشته باشد؛ برنامه نیز قابل‌دورزدن از لایهٔ حفاظت نباشد. شبکهٔ خصوصی staging نباید به شبکه یا پایگاه‌دادهٔ n8n متصل شود. فقط نحوهٔ ارتباط Caddy با برنامه پس از مشخص‌شدن محل اجرای Caddy تعیین می‌شود.
3. **ورودی محافظت‌شده:** گزارش زیرساخت در بررسی فعلی هیچ reverse proxy فعالی نیافته است؛ انتخاب proxy باز است. پیشنهاد بررسی Caddy یا گزینهٔ مورد تأیید با TLS و احراز هویت **برای کل host** شامل HTML، API، GraphQL، admin و media است؛ گزینهٔ تونل/VPN یا ترکیب با allowlist نیز باید با دستیار زیرساخت بررسی شود. صرف `/admin` یا `robots.txt` محافظت کل سایت نیست. دسترسی مستقیم به upstream، IPv4/IPv6، مسیرهای جایگزین و spoofing هدرهای proxy باید آزمون شوند. لایهٔ حفاظت قبل از هر اتصال اینترنتی برقرار و آزموده می‌شود.
4. **DB production:** بررسی اولیهٔ کد Payload 3.91.0 نشان می‌دهد schema push فقط خارج `NODE_ENV=production` اجرا می‌شود و CLI قابلیت `migrate:create`، `migrate` و `migrate:status` دارد؛ در مخزن فعلی migration نسخه‌بندی‌شدهٔ Payload وجود ندارد. دو فایل SQL فعلی صرفاً از طریق `db:init` توسعه اجرا می‌شوند و جدول `shared.customers` را پوشش می‌دهند، نه کل مدل Payload. بنابراین باید baseline migration تولیدی Payload و روش نسخه‌بندی و اجرای امن `website` و `shared.customers` طراحی، بازبینی و با دیتابیس تازه و مسیر ارتقا آزموده شود؛ `db:init` و schema push روش استقرار production فرض نمی‌شوند. `migrate:fresh`/`reset` یا rollback مخرب روی دادهٔ ماندگار استفاده نشود. رفتار schema آزمایشی `schemaName` و ترتیب ساخت schema و جدول migration باید با نسخهٔ پین‌شده عملاً تأیید شود.
5. **اولین Staff:** تا پیش از ساخت و تأیید حساب، هیچ مسیر برنامه از اینترنت در دسترس نباشد. روش پیشنهادی: بعد از migration و با اتصال محلی/تونل مدیریت محدود، نخستین حساب از UI اولیهٔ Payload ساخته شود؛ رمز مستقل تصادفی از مسیر امن و بدون ثبت در Git، لاگ، shell history یا گفتگو تحویل شود. بسته باید بررسی کند bootstrap پس از ایجاد حساب دوباره قابل سوءاستفاده نیست؛ هویت مالک، روش بازیابی و نحوهٔ تحویل باید پیش از اجرا تأیید شوند. اجرای اتوماتیک با credential در آرگومان CLI پیشنهاد نمی‌شود.
6. **Seed:** فقط محتوای مصوب در دیتابیس staging؛ قبل از اجرا رکورد موجود `track-record-intro` و سایر رکوردهای موجود بررسی می‌شوند. کد فعلی رکوردهای موجود را به‌صورت خودکار ویرایش نمی‌کند اما find/create اتمیک و امن برای اجرای هم‌زمان تضمین نشده است؛ seed باید به‌صورت یک عملیات تک‌اجرا، پس از migration و با بررسی نتیجه و تکرارپذیری آزموده شود. اجرای خودکار seed در هر restart ممنوع است. اسکریپت فعلی به `.env` و `tsx` وابسته است و سازگاری آن با ایمیج نهایی و محیط production هنوز آزموده نشده است.
7. **پایداری و بازگشت:** healthcheck سبک برنامه و readiness پایگاه‌داده بدون افشای اطلاعات داخلی؛ لاگ ساختاریافته، محدود و چرخشی بدون رمز، کوکی، Authorization، اتصال DB یا دادهٔ فرم. پیش از ارتقا backup رمزنگاری‌شدهٔ هماهنگ DB و فایل‌های آپلود با آزمون بازگردانی و ثبت نسخه/زمان تهیه شود. ایمیج قبلی با digest محفوظ بماند؛ بازگشت برنامه فقط در صورت سازگاری schema مجاز است و برای migration ناسازگار، بازیابی هماهنگ DB و فایل‌ها با پذیرش احتمال از دست‌رفتن تغییرات پس از backup لازم است. جزئیات retention و مقصد backup تأیید نشده‌اند.
8. **جلوگیری از دسترسی/اتصال ناخواسته:** علاوه بر احراز هویت، در پاسخ‌های staging هدر `X-Robots-Tag: noindex, nofollow` و robots مناسب، برای HTML و پاسخ‌های مرتبط طراحی و آزموده شود؛ این‌ها جایگزین حفاظت دسترسی نیستند. از canonical/sitemap اشاره‌کنندهٔ ناخواسته و ارسال ایمیل، اعلان، analytics و اتصال n8n/CRM جلوگیری شود. پروژه فعلاً یکپارچگی فعال از این انواع نشان نمی‌دهد؛ کنترل و آزمون fail-closed برای آینده هنوز لازم است.

## متغیرها و نمونهٔ غیرعملیاتی

این نمونه **صرفاً فهرست طراحی** است، نه فایل آماده یا تنظیمات پیاده‌سازی‌شده. مقادیر عمداً خالی‌اند؛ هیچ Secret در Git یا گفتگو قرار نگیرد. نام‌های احتمالی بعد از تأیید روش proxy و Compose نهایی می‌شوند.

```dotenv
# Used by the current Payload code; unique to staging.
DATABASE_URL=
PAYLOAD_SECRET=
# Needed only if the selected Compose runs its own staging PostgreSQL.
POSTGRES_USER=
POSTGRES_PASSWORD=
POSTGRES_DB=
# Proposed URL configuration; not yet consumed by this application.
PREVIEW_ORIGIN=
# Build/runtime configuration; verify actual injection and precedence.
NODE_ENV=
NEXT_TELEMETRY_DISABLED=
```

`DATABASE_URL` حاوی credential است و باید مانند Secret محافظت شود؛ `PAYLOAD_SECRET` طولانی و تصادفی و جدا از سایر محیط‌ها باشد. کد فعلی `serverURL`/CSRF/CORS ویژهٔ preview و متغیر `PREVIEW_ORIGIN` را تنظیم نکرده است؛ نام، اعتبارسنجی و استفادهٔ URL باید طراحی و آزموده شود. متغیرهای اتصال یا رمز احراز هویت proxy و روش تزریق امن آن‌ها تابع طرح Caddy/infra است؛ رمز Staff نباید یک متغیر ماندگار عمومی یا داخل آرگومان و لاگ باشد. `NODE_ENV=production` و رفتار build-time در بستهٔ نهایی باید تأیید شود. از چاپ raw env و `source .env` در shell مشترک خودداری شود.

## پرسش‌های ضروری از دستیار زیرساخت

۱. فازهای ۰/A واقعاً کامل و پایدارند؟ نسخهٔ OS، Docker/Compose، معماری CPU، مصرف فعلی و اوج RAM/CPU، swap، فضای آزاد و محدودیت‌های عملیاتی چیست؟ اطلاعات را بدون Secret ارسال کنید.
۲. Caddy اکنون نصب و فعال است یا فقط در طرح است؟ محل اجرا، نسخه، شبکه‌ها، اتصال مجاز به سرویس جدا و سیاست TLS/auth، IPv4/IPv6 و firewall چیست؟ کدام روش حفاظت کل preview (Caddy auth، VPN/SSH، allowlist یا ترکیبی) در زیرساخت پشتیبانی و توسط مالک تأیید می‌شود؟
۳. شیوهٔ مجاز DNS/TLS برای `preview.xennic.ir`، صدور و تمدید گواهی، وجود رکوردهای متعارض و مسئول تغییر چیست؟ در این مرحله هیچ رکوردی تغییر نمی‌کند.
۴. inventory بدون مقادیر محرمانهٔ نام Compose project/service/network/volume و پورت‌های اشغال‌شده چیست؟ نام‌های ایمن staging، ارتباط proxy بدون اشتراک شبکهٔ اتوماسیون، مسیر و مجوزهای volumeهای مجزا چگونه باشد؟
۵. سیاست پشتیبان رمزنگاری‌شدهٔ PostgreSQL و آپلودها، مقصد خارج از VPS، retention، بازیابی آزموده‌شده و RPO/RTO مورد انتظار چیست؟ چه کسی به کلیدها و backup دسترسی دارد؟
۶. build/transfer از کجا انجام می‌شود و دسترسی VPS به image registry و پکیج‌ها چگونه است؟ `META-INT-140` محدودیت‌های تاریخی npm/Docker Hub از IP ایران را ذکر می‌کند؛ وضعیت امروز و راهکار مجاز چیست؟
۷. محل مورد تأیید نگهداری و تزریق Secretهای جدید، تحویل امن credential نخستین Staff، محدودیت دسترسی اپراتورها و سیاست چرخش چیست؟ هیچ مقدار واقعی در پاسخ یا Git ارسال نشود.
۸. روش پایش، سقف resource و log rotation و مسیر واکنش به خرابی چیست؟ سلامت پیش‌نمایش نباید اعلان عملیاتی ناخواسته به n8n/CRM یا سامانه‌های موجود بفرستد.

## معیارهای تکمیل بسته، پیش از درخواست استقرار

- [ ] پاسخ‌های زیرساخت دریافت و انتخاب‌های اثرگذار، از جمله روش دسترسی محافظت‌شده، محل proxy، انزوای DB و volume، backup و مسیر ایمیج تأیید و در صورت نیاز ابتدا در Vault ثبت شوند.
- [ ] migration نسخه‌بندی‌شده با DB تازه و نسخهٔ قبلی، اجرای مجدد و حفظ داده، عدم schema push در production، failure/restore و `shared.customers` آزموده شود.
- [ ] ایمیج واقعاً build و با `npm run start` و Postgres staging اجرا شود؛ health/readiness، restart، volume، آپلود، پایایی و لاگ بدون Secret آزموده شود.
- [ ] نخستین Staff قبل از دسترسی اینترنتی ساخته و ورود و عدم امکان bootstrap مجدد تأیید شود؛ حفاظت کل host و عدم دورزدن مستقیم/IPv6 آزموده شود.
- [ ] seed روی دیتابیس تازه و دارای ویرایش اجرا و non-overwrite، عدم اجرای موازی و نمایش جملهٔ دقیق مصوب در صفحهٔ اصلی به‌صورت دستی و خودکار بررسی شود.
- [ ] پاسخ‌های noindex و ممنوعیت اتصال/اعلان، auth/API/media و نبود data/credential عملیاتی بررسی شوند؛ ثبت نتیجهٔ آزمایش و بازیابی از نسخهٔ قبل.
- [ ] audit و ریسک overrideها پیش از هر دسترسی بیرونی بازبینی شود؛ در ۲۰۲۶-۱۰-۳۰ audit وابستگی‌های runtime در این Sandbox صفر critical/high و ۵ moderate و ۷ low گزارش کرد، نه تضمین امنیت.

CI فعلی فقط build و smoke با **dev server** را پوشش می‌دهد و شاهد اجرای production نیست. بسته پس از دریافت پاسخ و آزمون‌های فوق آماده تلقی می‌شود؛ استقرار یا تغییر DNS به تصمیم و اقدام جداگانه نیاز دارد.


## اصلاحیهٔ این نشست: نمونهٔ آزمایشی، نه مجوز استقرار

گزارش زیرساخت: ۴ CPU، حدود ۵٫۸ GiB RAM، یک نمونهٔ RAM در دسترس حدود ۱٫۷ GiB و حدود ۵۳ GiB دیسک آزاد؛ کفایت ظرفیت **تأیید نشده** و reverse proxy فعال یافت نشد. هیچ فرضی دربارهٔ Caddy فعال یا registry نداریم. ساخت ایمیج خارج VPS انجام می‌شود؛ انتقال یا registry پس از بررسی دسترسی سرور تعیین خواهد شد.

- فایل‌های آزمایشی `Dockerfile.preview` و `compose.preview.yml`: Node 22.22.3، Next.js `next start` روی پورت ۳۰۰۰ داخل کانتینر، PostgreSQL 16.14 فقط در شبکهٔ Compose، پورت برنامه صرفاً loopback برای آزمون. project `xennic-preview-test` و volumeهای `preview_db` و `preview_media` مخصوص این نمونه‌اند؛ نام‌های واقعی پیش از استقرار باید بررسی شوند. محتوای `/app/media` پایدار است؛ volumeها و DB با هیچ محیط عملیاتی مشترک نشوند. هیچ یک از این تنظیمات یک proxy یا محافظ اینترنتی نیست.
- نمونهٔ خالی `.env.preview.example` شامل نام تنظیمات است. `PREVIEW_DATABASE_URL` و `PREVIEW_PAYLOAD_SECRET` محرمانه‌اند. `XENNIC_PREVIEW=1`، `NODE_ENV=production` و `MEDIA_DIR=/app/media` در ایمیج تعبیه شده‌اند. URL سایت و تنظیمات CSRF/CORS برای proxy واقعی هنوز نهایی نشده‌اند.
- در DB تازه، یک بار `npm run preview:migrate` و سپس `npm run preview:seed` **در کانتینر برنامه**، در حالی که برنامه عمومی نیست، اجرا شوند؛ هیچ‌یک در شروع خودکار اجرا نمی‌شود. wrapper با advisory lock، جداول بدون migration یا schema push توسعه‌ای را رد می‌کند؛ هم‌زمانی این دو کار مجاز نیست. baseline شامل schemaهای `website` و `shared.customers` است؛ ساخت مجدد یا rollback مخرب اتوماتیک ممنوع. DB قدیمی یا نامنطبق نیاز به بازبینی و مسیر ارتقای جداگانه دارد؛ برای DB تازه طراحی شده است.
- پیش از دسترسی اینترنتی، bootstrap حساب Staff با تونل/دسترسی محلی کنترل‌شده، تأیید ورود و منع ثبت مجدد لازم است. دامنه، هویت و انتقال امن credential و راهکار بازیابی هنوز تعیین نشده‌اند. ارسال ایمیل در حالت preview صریحاً غیرفعال است؛ قابلیت بازیابی ایمیلی در این محیط کار نمی‌کند.
- `tests/preview-production.mjs` یک proxy شبیه‌سازی‌شدهٔ فقط محلی با اعتبار جداگانه است، نه راهکار امنیتی نهایی. Basic Auth و Payload Bearer هر دو از هدر `Authorization` استفاده می‌کنند؛ با یک هدر نمی‌توان هر دو را هم‌زمان حمل کرد. آزمون ورود Staff، کوکی، API دارای Bearer و media از proxy آزمایشی می‌گذرد؛ طراحی نهایی TLS/auth، جلوگیری از bypass و همهٔ مسیرها همچنان نیاز به آزمون در زیرساخت نهایی دارند.
- healthcheck با اتصال DB روی `/health` است؛ هدر noindex در build پیش‌نمایش تنظیم می‌شود، نه جایگزین کنترل دسترسی. retention/backup و تست restore واقعی و حذف Secret از تمامی لاگ‌های upstream هنوز به بازبینی نیاز دارند.
- `production-preview` در CI Docker build و start واقعی و Postgres جدا را اجرا می‌کند؛ گزارش خروجی و اندازه‌گیری واقعی در گزارش این نشست ثبت می‌شود. اعداد Docker/runner تخمین بار VPS نیستند؛ build memory فقط به‌صورت تغییر RAM آزاد کل runner، نه حداکثر RAM فرایند build، نمونه‌برداری می‌شود.
