## انجام‌شده و نتیجه

- وضعیت زندهٔ PR #11 پیش از تغییر: باز، مقصد `dev`، head `9edb0b07df4cd0f2377ea3557a152835fa06c697`؛ هر سه job در [CI 41186812509](https://github.com/feerozmandi/xennic-website/actions/runs/41186812509) موفق و job انتشار در PR به‌درستی skipped بود. این شاهد انتشار یا استقرار نیست.
- شاخهٔ محلی با remote همگام شد؛ پیش از به‌روزرسانی index، فایل‌های tracked با head remote مقایسه و یکسانی آن‌ها تأیید شد. محتوای workspace بازنویسی نشد.
- workflow، پس از ساخت و انتشار image برای `dev` و پیش از اعلام موفقیت job، همان مرجع GHCR با digest خروجی build را برای `linux/amd64` دریافت و با همان مجموعهٔ آزمون production شامل migration، برنامه و بازیابی آزمایشی اجرا می‌کند. Image ID کانتینر App با image دریافت‌شده مقایسه می‌شود؛ خروجی موفق job هنوز deploy نیست. اگر آزمون شکست بخورد، artifact ممکن است در GHCR باقی بماند اما نباید deploy شود. Test روی PRها دسترسی انتشار یا secret استقرار ندارد.
- `scripts/ci-preview.sh` فقط project دورریختنی CI را می‌پذیرد و پیش از ایجاد cleanup، مرجع image و محیط را اعتبارسنجی می‌کند. `bash -n` و رد صریح محیط غیر CI و image نامعتبر در sandbox موفق بودند. اجرای واقعی Docker در sandbox انجام نشده است؛ job جدید و آزمون pull با digest فقط در اجرای `push` واقعی روی `dev` اثبات می‌شوند.

## مانع و اقدام بعدی

- deploy/SSH، قفل مشترک سمت سرور، backup رمزنگاری‌شده و restore، rollback سازگار، تأیید package/branch protection و پذیرش واقعی هنوز تکمیل یا آزموده نشده‌اند. API حفاظت شاخه در این نشست مجوز خواندن نداد؛ وضعیت واقعی نامعلوم است. دسترسی SSH یا اعتبار قابل استفاده در محیط این دستیار مشاهده نشده و هیچ اتصال یا تغییری به VPS و DNS انجام نشده است.
- **اصلاح ۲۰۲۶-۱۰-۳۱:** وجود منبع backup نزد مالک احراز نشده است. مقصد backup خصوصیِ **خارج از همان VPS** باید تعیین و تأیید شود؛ نباید هزینهٔ جدید، دسترسی اضافی یا تحویل secret در گفتگو فرض شود. نبود backup/restore معتبر مانع migration یا تغییر داده است، نه مانع پیشبرد کد و بررسی‌های مستقل.
- پس از تعیین مسیر همکاری، پیش‌پرواز فقط‌خواندنی شامل هویت host از منبع مستقل، endpoint، ظرفیت، پورت‌ها، وضعیت edge، DNS authority و تخصیص IP انجام شود؛ سپس کار deploy بر مبنای بخش ۱۰ قرارداد ادامه یابد. OAuth App نهایی و scope آن جدا از مجوز آزمایشی بررسی می‌شوند.
