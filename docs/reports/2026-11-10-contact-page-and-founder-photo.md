# صفحهٔ تماس، فرم واقعی و عکس مؤسس

## چه ساخته شد

سه چیز که مالک در یک پیام خواسته بود، در همین سیستم طراحی موجود و بدون چارچوب یا سرویس تازه پیاده شد:

1. **صفحهٔ تماس** با مسیرهای تأییدشدهٔ مالک (`/contact`).
2. **عکس واقعی مؤسس** در بخش پیشینهٔ صفحهٔ اصلی و در کارت مؤسس صفحهٔ تماس.
3. **فرم تماس واقعی** که پیام را در همان سامانهٔ Payload ثبت می‌کند و هیچ موفقیت جعلی نشان نمی‌دهد.

## فرم تماس

- پیاده‌سازی با Server Action (`src/lib/contact-actions.ts`)، بدون API عمومی تازه و بدون microservice.
- اعتبارسنجی با `zod`: نام و متن پیام الزامی، حداقل یک روش پاسخ (تلفن یا رایانامه)، قالب رایانامه و شماره بررسی می‌شود.
- تلهٔ ربات (honeypot) و محدودیت نرخ ساده: حداکثر ۵ ارسال در ۱۰ دقیقه برای هر نشانی.
- ثبت رکورد با `overrideAccess` روی مجموعهٔ موجود `lead-submissions` (`source=website-contact`, `status=new`). **مجموعه برای همهٔ فراخوانی‌های ناشناس همچنان ۴۰۳ است**؛ آزمون smoke همین را تضمین می‌کند.
- پیام موفقیت فقط پس از موفقیت واقعی درج رکورد نمایش داده می‌شود؛ در خطا پیام صادقانه با مسیر جایگزین (تلفن/رایانامه) نشان داده می‌شود.
- دسترس‌پذیری: برچسب برای هر فیلد، `aria-invalid` و `aria-describedby` برای خطاها، ناحیهٔ `aria-live` برای وضعیت، focus برنامه‌ای روی ناحیهٔ وضعیت پس از ارسال، دکمهٔ «در حال ارسال…» فقط در حین ارسال، و کارکرد بدون جاوااسکریپت (ارسال معمولی فرم).

### آزمون انتها-به-انتها

فرم با ارسال بدون جاوااسکریپت (همان مسیری که مرورگر با JS خاموش استفاده می‌کند) روی نسخهٔ production محلی آزموده شد:

| سناریو | نتیجه |
|---|---|
| ارسال معتبر | پیام موفقیت نمایش داده شد و رکورد در `website.lead_submissions` با `source=website-contact` ساخته شد |
| نام خالی و متن کوتاه | خطای فیلد به فیلد، بدون ساخت رکورد |
| متن پیام کوتاه‌تر از ۱۰ نویسه | همان |
| بدون تلفن و رایانامه | خطای «شمارهٔ تماس یا رایانامه را وارد کنید»، بدون رکورد |
| رایانامهٔ بدشکل | خطای قالب رایانامه، بدون رکورد |
| پر شدن honeypot | «درخواست نامعتبر است و ثبت نشد»، بدون رکورد |

## یک اشکال واقعی که در همین مرحله پیدا و رفع شد

نسخهٔ اول `contact-actions.ts` علاوه بر تابع، یک ثابت (`INITIAL_CONTACT_STATE`) هم صادر می‌کرد. Next در زمان اجرا با خطای «A "use server" file can only export async functions» آن ماژول را رد کرد؛ آزمون فرم این را آشکار کرد. ثابت و type به `src/lib/contact-form.ts` منتقل شدند و پس از آن مسیر ارسال درست کار کرد. این نشان می‌دهد آزمون انتها-به-انتها لازم بود، چون `next build` و `tsc` این خطا را نشان نمی‌دادند.

## ریسک‌ها و کارهای باز

| مورد | وضعیت |
|---|---|
| اعلان ایمیلی | **پیکربندی نشده.** پیام‌ها فقط در پنل `/admin` (مجموعهٔ «درخواست‌های تماس») دیده می‌شوند؛ هیچ رونوشتی به `info@xennic.ir` نمی‌رود. برای اعلان، SMTP تأییدشده لازم است. |
| نشانی اینستاگرام | از هندل ساخته شده؛ مالک باید یک بار باز شدن نمایه را تأیید کند. |
| منبع دادهٔ تماس در Vault | این مقادیر در Vault ثبت نشده‌اند؛ در نشست مستندسازی باید به سند تأییدشده منتقل شوند تا منبع یگانهٔ رسمی بماند. |
| محل ذخیرهٔ پیام‌ها | روی همان پایگاه‌دادهٔ سایت است؛ پشتیبان `manual-local` فعلی آن را پوشش می‌دهد ولی انتقال دستی خارج VPS هنوز انجام نشده. |
| محدودیت نرخ | در حافظهٔ همان نمونه است؛ با چند نمونهٔ هم‌زمان کار نمی‌کند و برای حجم بالا به ذخیره‌گاه مشترک نیاز دارد. |
