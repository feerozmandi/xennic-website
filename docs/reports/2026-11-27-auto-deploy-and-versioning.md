# استقرار خودکار پس از هر merge به `dev`، و نسخه‌بندی خودکار

- **تاریخ:** ۲۰۲۶-۱۱-۲۷
- **شاخه:** `arena/cf13d19d-xennic-website`
- **تصمیم مالک:** پس از هر merge به `dev` سایت و ایمیج تولید روی VPS **بدون فرایند دستی** به‌روزرسانی شود؛ نسخه‌بندی انتشار هم خودکار باشد؛ دروازهٔ گذارِ migration **بماند** ولی برای گذارهای امن خودکار تأیید شود.
- **وضعیت:** کد و آزمون‌ها آماده است. **نصب روی میزبان هنوز انجام نشده**؛ تا اجرای دستورهای بخش ۶، رفتار میزبان همان رفتار پیشین است.

## ۱) چه چیزی تغییر کرد

پیش از این، هر merge به `dev` سه چیز را لازم داشت که هیچ‌کدام خودکار نبود:

1. کسی باید **ردیف گذارِ reviewed** را برای جفت `from_commit → to_commit` می‌ساخت (دستور `approve-transition.sh`)،
2. کسی باید **می‌خواند که گذار چه اثری دارد**،
3. کسی باید **نسخهٔ انتشار** را تعیین می‌کرد.

اکنون هر سه حذف یا خودکار شده‌اند:

| کار | پیش از این | اکنون |
| --- | --- | --- |
| ردیف گذار | هر merge یک اجرای دستی | خودکار، **فقط** وقتی گذار ثابت‌شده بی‌خطر باشد |
| تشخیص بی‌خطری | خواندن دستیِ diff | سه شرط ماشینی روی ایمیج و پایگاه‌داده |
| نسخه | تعیین دستی | `v<major>.<minor>.<patch>` از پیام commitها، **در CI**، به‌صورت تگِ گیت روی کامیتِ انتشار و تگِ دوم روی ایمیج |
| گذارِ مهاجرت‌دار | یک اجرای دستی | **همچنان دستی** — دروازه سر جایش ایستاده |

## ۲) زنجیرهٔ تازه

```
xennic-pull-deploy.timer  (هر ۵ دقیقه، systemd، root)
   └─ ci-pull-deploy
        ├─ ۱. قفل مشترک استقرار (نبودِ قفل ⇒ خروج بی‌صدا)
        ├─ ۲. GitHub: آخرین run موفق push روی dev، و همان commit باید head فعلی dev باشد
        ├─ ۳. artifact همان run دانلود و به run_id/commit/run_number قفل می‌شود
        ├─ ۴. مقایسه با ژورنال release-state.json (همان نسخه؟ ⇒ خروج بی‌صدا)
        ├─ ۵. ردیف گذار reviewed هست؟
        │      نه  ⇒ کلید خودکار خاموش است؟ ⇒ waiting-approval + اعلان + خروج
        │      کلید خودکار روشن است ⇒ ادامه (تصمیم با backend است، نه با این برنامه)
        ├─ ۶. همان preview-deploy-backend.py با همان پروتکل دو خطی (مانیفست + توکن)
        │      └─ release-check: گذار را بررسی می‌کند؛ نبودِ ردیف ⇒ قاعدهٔ خودکار را می‌سنجد
        │            ├─ ردیف reviewed هست ⇒ همان را به کار می‌برد
        │            └─ نبودِ ردیف ⇒ قاعدهٔ خودکار: ایمیج کاندیدا کشیده می‌شود،
        │                  درختِ مهاجرتِ آن با درختِ مهاجرتِ نسخهٔ زنده سنجیده می‌شود،
        │                  ledger پایگاه‌داده با نام‌های اعلام‌شده سنجیده می‌شود،
        │                  و در صورت تساوی ردیفِ reviewed نوشته می‌شود
        │      └─ اگر هیچ‌کدام نبود ⇒ استقرار **پیش از هر تغییری روی میزبان** متوقف می‌شود
        └─ ۷. بررسی عمومی https://xennic.ir/robots.txt، ثبت نسخه، و اعلان نتیجه
```

نکتهٔ مهمِ ترتیب: **قاعدهٔ خودکار پیش از `mark_inflight` سنجیده می‌شود**، یعنی پیش از آنکه ژورنال قفل شود و پیش از آنکه سایت به حالت تعمیر برود. اگر گذار امن نبود، میزبان **دست‌نخورده** می‌ماند و فقط یک اعلان «منتظر تأیید» می‌رود — همان رفتاری که پیش از این بود.

## ۳) قاعدهٔ خودکار: چه چیزی «بی‌خطر» است

یک گذار فقط وقتی خودکار تأیید می‌شود که هر سه شرط برقرار باشند:

| شرط | چرا | کجا سنجیده می‌شود |
| --- | --- | --- |
| کلید خودکارِ مالک روشن است | تصمیم مالک است، نه تصمیم برنامه | `/srv/xennic-preview/config/auto-approval.json` |
| **درختِ مهاجرتِ ایمیج کاندیدا با درختِ مهاجرتِ نسخهٔ زنده یکی است** (هش محتوا) | اگر فایل‌های مهاجرت یکی باشند، schema عوض نمی‌شود | هشِ همان درختی که `migrate` هم استفاده می‌کند |
| **نام‌های اعلام‌شدهٔ ایمیج دقیقاً برابرِ ledger پایگاه‌دادهٔ زنده است** | یعنی `preview:migrate` هیچ مهاجرتی اجرا نمی‌کند؛ schema دست‌نخورده می‌ماند | `website.payload_migrations` روی دیتابیس زنده |

نتیجه: **schema تغییر نمی‌کند** ⇒ rollback به ایمیل قبلی امن است ⇒ همان چیزی که `rollback_safe: true` در ردیف گذار ادعا می‌کند، اینجا **اثبات** می‌شود، نه ادعا.

نکتهٔ دیگر: ردیفی که خودکار نوشته می‌شود، **همان شکل ردیفِ دستی** را دارد و در همان فایل `compatible-transitions.json` می‌نشیند (پشتیبان هم می‌گیرد). پس سابقهٔ «چه چیزی تأیید شد» کامل و قابل بازرسی می‌ماند.

و چون شرط اول «درخت یکی» و شرط دوم «ledger برابر» است، **هر تغییرِ schema همچنان به انسان نیاز دارد** — دقیقاً همان چیزی که مالک خواست.

## ۴) نسخه‌بندی خودکار و نامِ انتشار

**نامِ انتشار را CI می‌سازد و مخزن آن را نگه می‌دارد**: یک تگِ گیت روی کامیتی که منتشر می‌شود (`v1.2.3`) و همان نام به‌عنوان تگِ دوم روی ایمیجِ منتشرشده. نام از تگ‌های انتشارِ خودِ مخزن و پیامِ commitهای بینِ آن‌ها حساب می‌شود:

| نشانه در پیام commit | اثر روی نسخه |
| --- | --- |
| `BREAKING CHANGE:` در بدنه، یا `!` بعد از نوع | بزرگ‌تر می‌شود: `v2.0.0` |
| نوع `feat` | کوچک‌تر می‌شود: `v1.3.0` |
| هر چیز دیگر (`fix`، `docs`، `ci`، …) | وصله می‌شود: `v1.2.4` |

پایهٔ حساب، **بالاترین نسخهٔ انتشاری است که در تاریخچهٔ همین کامیت هست** (یعنی تگِ انتشارِ قبلی)، پس شماره فقط رو به جلو می‌رود. اگر هیچ تگِ انتشاری در تاریخچه نباشد، این اولین انتشارِ خط است و `v1.0.0` می‌شود. نامی که کامیتِ دیگری گرفته دوباره استفاده نمی‌شود، و یک کامیت هر بار که نام‌گذاری شود **همان** نام را می‌گیرد (پس اجرای دوبارهٔ همان run، انتشار تازه به نظر نمی‌رسد).

سه نکتهٔ مهم:

1. **تگ فقط بعد از آزمونِ ایمیجِ منتشرشده ساخته می‌شود.** یعنی یک نام روی یک کامیت یعنی «این ایمیج آزموده شده است». اگر آزمون‌ها شکست بخورند، مخزن برای آن کامیت بی‌نام می‌ماند و انتشاری در کار نیست.
2. **verifier نام را الزام می‌کند**: انتشاری که کامیتش دقیقاً یک تگِ `vX.Y.Z` ندارد، انتشار نیست و `release-check` آن را رد می‌کند (fail-closed).
3. **میزبان نام را از همان API عمومی می‌خواند** و در ژورنال ثبت می‌کند. نامی که نسخهٔ زنده را جلو نمی‌برد پذیرفته نمی‌شود، و اگر خواندنِ تگ ممکن نبود، **حسابِ قدیمیِ** مبتنی بر پیامِ commitها به کار می‌افتد — یعنی خواندنِ تگ **هرگز** استقرار را متوقف نمی‌کند.

نسخه کجا دیده می‌شود:

- تگِ گیت روی کامیت (`v1.2.3`) و تگِ دوم روی ایمیج در GHCR،
- `release-state.json` (ژورنالِ authoritative) → کلید `release_version`،
- `state/pull-deploy.json` (رکوردِ استقرار) → `release_version`،
- پیام اعلان («run ۲۷۱ (a1b2c3d) v1.3.0 is live»).

**شمارهٔ run** هم، مثل گذشته، در خودِ مانیفستِ انتشار (`run_number`) و در ژورنال ثبت است؛ یعنی هر انتشار **هم** با شمارهٔ run و **هم** با نامِ semver شناخته می‌شود.

## ۶) دستورهای اعمال روی VPS

همه به‌عنوان root، روی همان میزبانی که timer و gateway روی آن نصب است.

### ۶.۱) همه‌چیز، در یک بلوک

این بلوک را **یک‌جا** اجرا کنید. دو گام هستند و ترتیبشان مهم است: اسکریپت باید **اول** روی میزبان باشد، وگرنه
اجرای گامِ دوم با `No such file or directory` می‌شکند.

```bash
set -euo pipefail
cd /root

# کامیت را از خودِ مخزن می‌خوانیم تا این دستور هرگز کهنه نشود. بهتر است
# کامیتِ دقیقِ همان merge باشد، نه نامِ شاخه: helperها از همان کامیتی گرفته
# می‌شوند که CI آزموده و منتشر کرده است.
COMMIT=$(curl -fsSL https://api.github.com/repos/feerozmandi/xennic-website/commits/dev \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["sha"])')
echo "commit: $COMMIT"

# گامِ اول: خودِ اسکریپت، از همان کامیت.
curl -fsSL -o refresh-preview-pull-deploy.sh \
  "https://raw.githubusercontent.com/feerozmandi/xennic-website/$COMMIT/scripts/refresh-preview-pull-deploy.sh"
chmod 700 refresh-preview-pull-deploy.sh

# گامِ دوم: تازه‌سازیِ همه‌چیز از همان کامیت.
/root/refresh-preview-pull-deploy.sh "$COMMIT"
```

### ۶.۲) پیش‌نیازها، پیش از هر تغییری

این‌ها **فقط‌خواندنی**‌اند و هیچ چیزی را تغییر نمی‌دهند. اگر یکی نبود، همان‌جا متوقف شوید؛ مسیرِ
`--refresh` روی میزبانی کار می‌کند که **قبلاً** مجموعهٔ helperها را داشته باشد، چون کارش جابه‌جاییِ
`/usr/local/libexec/xennic-preview` است.

```bash
ls -ld /usr/local/libexec/xennic-preview          # مجموعهٔ helperهای ثابت
ls -l  /root/.xennic-release-token                 # توکن انتشار (مقدارش را نخوانید)
systemctl is-active xennic-pull-deploy.timer || echo "timer فعال نیست"
```

فهرستِ زندهٔ نام‌ها و کامیت‌هایشان:

```bash
gh api repos/feerozmandi/xennic-website/tags --jq '.[] | "\\(.name) -> \\(.commit.sha)"'
```

### ۶.۲.۱) اگر refresh را دوباره اجرا می‌کنید

refresh مجموعهٔ helperها را **جابه‌جا** می‌کند و نسخهٔ پیشین را در
`/usr/local/libexec/.xennic-preview-before-refresh` نگه می‌دارد. پس **اجرای دومِ** refresh تا وقتی
آن نسخه پاک نشده رد می‌شود، با این پیام:

```
Fixed preview helper installation refused: previous or incomplete helper refresh exists: /usr/local/libexec/.xennic-preview-before-refresh — ...
```

این رد شدن **درست** است: جایی برای نگه‌داشتنِ نسخهٔ پیشینِ دیگری نیست، و یک refreshِ نیمه‌کاره نباید
پاک شود. وقتی مجموعهٔ فعلی را دیدید و از آن مطمئن شدید، نسخهٔ پشتیبان را بردارید و دوباره اجرا کنید:

```bash
ls -ld /usr/local/libexec/.xennic-preview-before-refresh
rm -rf /usr/local/libexec/.xennic-preview-before-refresh
```

> در shellِ تعاملیِ root از `set -e` استفاده نکنید: با اولین فرمانِ ناموفق، پوسته می‌بندد و نشستِ SSH
> قطع می‌شود. `set -euo pipefail` را داخل یک اسکریپت بگذارید، نه در پوستهٔ تعاملی.

این یک دستور چهار کار می‌کند و هیچ‌کدام استقرار نمی‌کند:

1. **helperهای ثابت** (`preview-fixed-operations.py`، `preview-deploy-state.py`، `preview-deploy-transaction.py`، `preview-deploy-backend.py`، …) را از همان کامیت می‌گیرد و با مسیر تازهٔ `--refresh` نصب‌کنندهٔ بررسی‌شده جایگزین می‌کند. مسیر تازه روی میزبانِ **در حال سرویس** کار می‌کند: ریشهٔ preview، ژورنال، فایل compose و گیت‌وی را **نه می‌خواند و نه می‌نویسد**، قفل استقرار را می‌گیرد، و مجموعهٔ قبلی را نگه می‌دارد.
2. **deployer، ماژول evidence و backend** را تازه می‌کند (همان کاری که این اسکریپت از قبل می‌کرد) و timer را دوباره فعال می‌کند.
3. **gateway تأیید** را اگر نصب باشد تازه می‌کند.
4. **تشخیصِ فقط‌خواندنی** را اجرا می‌کند و وضعیت واقعی را چاپ می‌کند (توکن چاپ نمی‌شود).

خروجیِ موفق این مرحله باید این را نشان دهد:

```
Fixed preview helpers refreshed; the previous set is preserved; no deployment started.
pull deployer installed: <sha256> (<bytes> bytes)
```

### ۶.۳.۱) یک آزمون که دو نیمهٔ اثبات را به هم وصل می‌کند

اثباتِ نسخهٔ زنده دو نیمه دارد که تا این لحظه جدا از هم آزموده می‌شدند: deployer نسخه‌ای را که از
مخزن خوانده در ژورنال می‌نویسد، و تشخیص همان ژورنال را می‌خواند و نامِ مخزن را با آن می‌سنجد. تغییرِ
هر نیمه به‌تنهایی، یا تغییر در شکلی که بر سرِ آن توافق دارند، هر دو را سبز نگه می‌داشت و اثبات روی
میزبان از کار می‌افتاد.

`tests/preview-deploy-state-diagnose.py` هر دو نیمه را روی **یک ژورنال** اجرا می‌کند: ژورنالی که
deployer می‌نویسد، همان‌طور که هست خوانده می‌شود. چهار حالت سنجیده می‌شود — توافق (خروج ۰)،
ناهماهنگی (`ANOMALY` و خروج ۱)، نسخه‌ای که پیش از نام‌گذاری مستقر شده (نه خطاست و نه `ANOMALY`)، و
کامیتی که نام دارد ولی ژورنالش نسخه ندارد. این suite در `ci.yml` هم اجرا می‌شود.

### ۶.۴) آزمودن پیش از آنکه چیزی خودکار برود

```bash
# ۱) وضعیت زندهٔ ژورنال
sudo cat /srv/xennic-preview/state/release-state.json

# ۲) تصمیمِ خشکِ استقرار: بدون هیچ تغییری
/usr/local/libexec/xennic-preview/ci-pull-deploy --dry-run

# ۳) اجرای یک‌بارهٔ واقعی (timer همین کار را می‌کند)
systemctl start xennic-pull-deploy.service
journalctl -u xennic-pull-deploy.service -n 40 --no-pager

# ۴) نامِ انتشار باید در ژورنال و در مخزن یکی باشد
#    تشخیصِ فقط‌خواندنی این را خودش می‌سنجد و اگر ناهماهنگ باشد
#    با «ANOMALY» و کد خروجِ ۱ می‌ایستد (نه «FAILED»: در آن حالت چیزی
#    نایستاده و فقط اثبات نادرست است).
python3 /root/xennic-preview-pull-deploy/diagnose-preview-pull-deploy.py

#    (یا به‌صورت دستی)
sudo grep release_version /srv/xennic-preview/state/release-state.json
gh api repos/feerozmandi/xennic-website/tags --jq '.[].name'
```

اگر `dry-run` چیزی جز `dry-run: would deploy` نداد، یعنی یا گذارِ reviewed برای جفت commitها نیست یا کلید خودکار خاموش است. اگر کلید خودکار روشن باشد و گذار امن باشد، `dry-run: would deploy` می‌دهد.

در بند ۴، مقدار `release_version` در ژورنال باید **همان** نامی باشد که در مخزن تگ شده است؛ اگر نبود، یعنی خواندنِ تگ روی این میزبان ممکن نبوده و نسخه از پیامِ commitها حساب شده است (که کار می‌کند، ولی نامِ مخزن را نشان نمی‌دهد).

بخشِ «the name of the live release» در خروجیِ تشخیص همین را **ماشینی** می‌سنجد: نامی که مخزن به کامیتِ زنده می‌دهد با مقدارِ `release_version` در ژورنال سنجیده می‌شود، و اگر یکی نباشند، تشخیص آن را `ANOMALY` می‌نامد و با کد خروجِ ۱ می‌ایستد. پس اثباتِ نهایی یک دستور است، نه یک مقایسهٔ چشمی.

**انتظارِ دقیق بعد از استقرار:** ژورنال باید `current.commit` را روی کامیتِ مستقرشده بگذارد و
`release_version` را برابرِ نامِ مخزن بنویسد (این نام را deployer از همان تگِ `vX.Y.Z` می‌خواند، نه
از پیامِ commitها). آن‌وقت بخشِ «the name of the live release» باید این را بگوید:

```
the live version is v1.2.4, and the repository names the live commit the same
```

و نتیجه:

```
== result
   The live release is v1.2.4, and that is the name the repository gives it.
   Every step of the release read works from this host.
```

**اگر به‌جای آن گفت** `the repository names no release for the live commit ...`، یعنی نسخهٔ زنده
هنوز همان نسخهٔ **پیش از نام‌گذاری** است (کامیتی که نه تگ دارد و نه `release_version`). این خطا نیست و
`ANOMALY` هم نیست: یعنی هنوز استقرارِ تازه انجام نشده. برای دیدنِ این حالت، ژورنال را بخوانید:

```bash
cat /srv/xennic-preview/state/release-state.json
```

این `ANOMALY` عمداً `FAILED` نیست: `FAILED` یعنی «deployer اینجا می‌ایستد»، و در این حالت چیزی نایستاده — استقرار تمام شده و سالم است. آنچه نادرست است **اثبات** است، و صاحبِ میزبان باید آن را ببیند.

### ۱۱.۱) اثباتِ زنده، روی APIِ واقعیِ گیت‌هاب

`tests/preview-pull-diagnose-live-api.py` همان تشخیص را روی **مخزنِ واقعی** اجرا می‌کند، نه روی fixture: تگ‌ها، اجرای `dev` و فهرست artifactها همه از APIِ واقعی خوانده می‌شوند. تنها چیزی که ساختگی است، دانلودِ خودِ ZIP است، چون GitHub آن را به ذخیره‌سازیِ خودش redirect می‌کند و sandbox نمی‌تواند به آن TLS بزند؛ پوشه از روی همان اجرایی که API گزارش کرده بازساخته می‌شود.

برنامه اثبات را **دو بار** انجام می‌دهد: یک بار با ژورنالی که راست می‌گوید، و یک بار با ژورنالی که نامی را ادعا می‌کند که مخزن نمی‌دهد. اولی باید بگذرد و دومی باید رد شود، وگرنه اثبات چیزی را ثابت نمی‌کند. نتیجهٔ واقعی روی commit `0c5db0b` (آخرین انتشار):

the repository names the commit 0c5db0b as v1.2.0

########## TRUTH — the host journal says v1.2.0 ##########
== workflow runs

== release evidence artifact
   xennic-preview-release-2: id 15235186187, 376 bytes
== evidence envelope

== the name of the live release

== result

########## LIE — the host journal claims a name the repository does not give ##########

### ۱۲.۳) آنچه عوض شد: `scripts/preview-release-tag.py`

گامِ تگ دیگر در پوستهٔ درونِ workflow نوشته نشده است. یک اسکریپتِ جدا آن را انجام می‌دهد و **هر پاسخِ ممکنِ API** در آن نوشته شده است:

1. **خواندن، خودِ ref است.** به‌جای `GET /commits/{name}` (که نام را با یک commit اشتباه می‌گیرد و برای نامِ آزاد صفحهٔ خطای ۴۲۲ روی stdout می‌دهد)، از `GET /git/ref/tags/{name}` پرسیده می‌شود: ۴۰۴ یعنی نام آزاد است، و هر پاسخِ دیگری یک **ردّ** است، نه «نام آزاد» — چون اجرا حق ندارد وقتی نمی‌تواند مخزن را بخواند، خودش نام را آزاد فرض کند. تگِ annotated هم تا commitِ داخلش باز می‌شود.
2. **نوشتن، idempotent است.** نامی که همین commit را می‌نامد، موفقیت است (اجرای دوبارهٔ یک انتشار، انتشارِ تازه به نظر نمی‌رسد). نامی که commitِ دیگری را می‌نامد، رد می‌شود (دو انتشار هرگز یک نام ندارند).
3. **نوشتنی که API رد کند، دوباره خوانده می‌شود.** ممکن است نوشتن به API رسیده باشد ولی پاسخش به این اجرا نرسیده باشد؛ پس نام یک بار دیگر خوانده می‌شود. اگر به همین commit اشاره کند، موفقیت است؛ اگر به commitِ دیگری، رد است.
4. **پاسخِ گذرا دوباره پرسیده می‌شود** (۴ بار، با فاصله)، ولی پاسخِ ۴۰۳ یا ۴۲۲ تکرار نمی‌شود.
5. **نام بعد از نوشتن خوانده و تأیید می‌شود** و تنها در صورتی پذیرفته می‌شود که واقعاً به همان commit اشاره کند. خطِ خلاصهٔ آن در `GITHUB_STEP_SUMMARY` نوشته می‌شود: مدرکِ اینکه مخزن نام را دارد.
6. **دلیلِ هر ردّ، یک خطِ `::error::` است.** یعنی شکستِ بعدی **کنارِ گامِ شکست‌خورده** دیده می‌شود و دیگر نیازی به باز کردنِ لاگ ندارد — همان چیزی که runِ ۳۱۷ نداشت.

### ۱۲.۴) آزمون‌ها

`tests/preview-release-tag.py` دوازده آزمون دارد که به اسکریپت یک `gh`ِ خودشان را می‌دهند: یک برنامهٔ کوچک که مثل API جواب می‌دهد، شامل همهٔ راه‌هایی که API می‌تواند رد کند (۴۰۴، ۴۰۳، ۴۲۲ «قبلاً هست»، ۴۲۲ «sha ناشناخته»، ۵۰۰ گذرا، تگِ annotated). نام‌های قابلِ بازگشت با این آزمون‌ها ثابت شده‌اند:

| حالت | نتیجه |
|---|---|
| نام آزاد | نوشته شد، خوانده شد، تأیید شد، خلاصه نوشته شد |
| صفحهٔ خطای نامِ آزاد (همان باگِ runِ ۲۹۵) | نام آزاد است، نه «گرفته‌شده» |
| نام از قبل همین commit را می‌نامد | موفقیت |
| نام commitِ دیگری را می‌نامد | ردّ با `::error::` |
| نوشتن با اجرای دیگر مسابقه داده و به همین commit رسیده | موفقیت |
| نوشتن با اجرای دیگر مسابقه داده و به commitِ دیگری رسیده | ردّ با `::error::` |
| پاسخِ ۵۰۰ گذرا | دوباره پرسیده شد و موفق شد |
| ردّ با ۴۰۳ | ردّ با `::error::` که **دلیلِ API** را نقل می‌کند |
| نامی که خوانده نمی‌شود | ردّ (اجرا چیزی نمی‌نویسد) |
