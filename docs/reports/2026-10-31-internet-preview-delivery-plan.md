# طرح اجرایی پیش‌نمایش اینترنتی و تحویل خودکار

- **تاریخ:** ۲۰۲۶-۱۰-۳۱
- **مبنا:** [PR شمارهٔ ۱۱](https://github.com/feerozmandi/xennic-website/pull/11)، وضعیت `dev` و تصمیم‌های مالک در همین گفتگو؛ این گزارش در همان PR برای بررسی است.
- **وضعیت:** چهار نیاز محصول تأیید شده‌اند؛ جزئیات مشترک با زیرساخت و طرح اجرایی نهایی در انتظار هماهنگی و تأیید یک‌جای مالک است. هیچ مجوز اجرای اولیه روی VPS یا تغییر DNS داده نشده است.

## خلاصهٔ مدیریتی

هدف، دسترسی محافظت‌شده از اینترنت به `https://preview.xennic.ir`، بدون تونل در استفادهٔ روزمره، برای کاربران مجاز و چند دستگاه هم‌زمان است. `feerozmandi` عضو اولیه است و افزودن کاربران دیگر با تأیید مالک انجام می‌شود. دامنهٔ اصلی برای انتشار نهایی محفوظ است. بازشدن سایت در lab محلی به گزارش مالک، معادل در دسترس بودن این آدرس از اینترنت یا پذیرش کامل gate نیست.

## طرح پیشنهادی مشترک

1. **ورود و نشست — زیرساخت:** استفاده از مسیر انتخاب‌شدهٔ Caddy، OAuth2 Proxy و GitHub OAuth بدون بازطراحی یا ساخت بستهٔ تکراری. فهرست مجاز قابل توسعه باشد. نشست gate حداکثر ۸ ساعت، بدون ورود دائمی و بدون refresh تمدیدکنندهٔ نامحدود باشد؛ logout کوکی همان مرورگر را پاک کند و دستگاه‌های دیگر را خارج نکند. در مدل cookie، نسخهٔ قبلاً کپی‌شده ممکن است تا انقضا معتبر بماند؛ حذف cookie gate از درخواست upstream و محافظت از آن ضروری است. ابطال اضطراری همهٔ نشست‌ها با چرخش امن کلید امضای/رمزگذاری cookie و راه‌اندازی کنترل‌شدهٔ gate مستند و در محیط مجاز آزموده شود؛ این اقدام همهٔ دستگاه‌ها را خارج می‌کند. اعتبار و logout نشست Payload جدا از gate است. احراز هویت چند دستگاه و انقضای واقعی ۸ساعته باید با gate نهایی اثبات شود. پس از انقضا ورود تازه به gate لازم است؛ GitHub ممکن است با نشست فعال خودش این ورود را بدون درخواست دوبارهٔ رمز انجام دهد.
2. **آزمون و ایمیج — وب‌سایت:** PRها فقط آزمون می‌شوند. پس از push به `dev`، همان سه job آزمون روی کامیت push اجرا می‌شوند؛ فقط در موفقیت همه، `Dockerfile.preview` برای `linux/amd64` خارج از VPS ساخته و در GHCR با tag حاوی SHA و digest در خلاصهٔ GitHub منتشر می‌شود. Workflow به سرور متصل نمی‌شود و هیچ credential استقرار در PRها قرار نمی‌گیرد. برای آنکه push به `dev` فقط ادغام تأییدشده باشد، حفاظت شاخه و منع push مستقیم باید تأیید شود؛ این workflow به‌تنهایی آن را تضمین نمی‌کند.
3. **استقرار — زیرساخت با اتصال سمت GitHub:** پس از توافق قرارداد و تأیید نهایی، فقط نتیجهٔ موفق همین اجرا و digest تغییرناپذیر به مسیر مدیریتی امن ارسال شود. سرور فقط همان digest را از GHCR دریافت کند؛ هویت استقرار اختصاصی، حداقل مجوز، و تأیید کلید میزبان SSH یا سازوکار معادل ضروری است. رمزها خارج از Git و گفتگو و خارج از دسترس workflowهای PR نگهداری شوند. مالکیت بسته، مجوز pull، هویت و قالب پاسخ/وضعیت باید با دستیار زیرساخت نهایی شوند. استقرار و نتیجهٔ سلامت/بازگشت باید در GitHub برای همان کامیت مشخص شود؛ انتشار ایمیج به‌تنهایی موفقیت استقرار نیست.
4. **ترتیب و بازیابی — زیرساخت:** استقرارها سریالی و بدون هم‌پوشانی باشند؛ طراحی صف باید رفتار چند merge سریع را روشن کند و از قرارگرفتن نسخهٔ قدیمی روی نسخهٔ جدید جلوگیری کند. محدودسازی معمول concurrency در GitHub ممکن است اجرای pending را جایگزین کند و به‌تنهایی تضمین اجرای تک‌تک mergeها نیست. قبل از migration پشتیبان لازم DB و media و بازیابی آن بررسی شود. migration با کنترل خطا و سیاست سازگاری expand/contract انجام شود؛ seed در انتشارهای عادی تکرار نشود. پس از healthcheck، نسخهٔ قبلی نگه‌داری شود؛ در شکست به نسخهٔ سازگار برگردید. بازگشت ایمیج، migration ناسازگار را برنمی‌گرداند؛ اگر بازیابی امن یا حفظ داده تضمین نیست، تغییر متوقف و تصمیم بازیابی گرفته شود، نه بازگردانی کورکورانهٔ DB.
5. **راه‌اندازی اولیه — فقط پس از تأیید:** زیرساخت منابع VPS، firewall، Caddy/HTTPS، secretها، backup، مسیر مدیریت، و DNS پیشنهادی `preview A 185.192.113.85` را پس از تأیید یک‌جای طرح آماده و اجرا می‌کند. دامنهٔ اصلی تغییر نمی‌کند. صحت مالکیت IP، تعارض رکوردهای موجود و تنظیمات نهایی باید پیش از تغییر بررسی شود. پس از راه‌اندازی اولیه، انتشارهای عادی باید خودکار باشند.
6. **پذیرش نهایی مشترک:** دو دستگاه مستقل و چند نشست هم‌زمان، حساب مجاز و دوم/غیرمجاز با هماهنگی، logout یک دستگاه و تداوم دیگری، انقضا و ابطال اضطراری، Origin مجاز/نامجاز/غایب، cookie/API/Bearer/GraphQL/media، bypass، TLS عمومی و RTL/menu/responsive، به‌علاوهٔ شکست استقرار و بازگشت سازگار بررسی شوند. نشست، scope و consent واقعی و علت قطعی خطای 403 پیشین هنوز مستقل تأیید نشده‌اند. آزمون مصنوعی یا CI جای این پذیرش را نمی‌گیرد.

## اقدامات و شواهد این نشست

- `.github/workflows/ci.yml` علاوه بر PR، push به `dev` را آزمون می‌کند و job انتشار GHCR فقط پس از موفقیت همهٔ jobها و صرفاً در push به `dev` فعال است. دسترسی `packages: write` فقط به job انتشار داده شده؛ عملگرهای Docker جدید با SHA ثابت ارجاع شده‌اند. اجرای workflow روی PR انتشار یا استقرار انجام نمی‌دهد.
- در ۲۰۲۶-۱۰-۳۱، YAML با PyYAML در sandbox خوانده و trigger، وابستگی به سه job، سطوح مجوز، معماری، tag/digest و نبود گام SSH به‌صورت ایستا بررسی شد. `git diff --check` نیز پیش از commit اجرا می‌شود. این بررسی‌ها اجرای GitHub Actions یا انتشار واقعی GHCR نیستند. دریافت ابزار `actionlint` به علت محدودیت دسترسی شبکه به asset انتشار موفق نشد.
- آزمون Docker یا runtime جدید در sandbox، اتصال به رایانهٔ مالک، انتشار واقعی ایمیج، استقرار، تغییر زیرساخت یا DNS انجام نشده است. CI مرتبط با تغییر جدید را باید در PR بررسی کرد؛ تست push/انتشار فقط پس از ادغام و آماده‌بودن مجوز GHCR قابل اثبات است. آزمون production موجود و ساخت ایمیج منتشرشده دو build جدا هستند؛ یکسانی digest آزمون‌شده و منتشرشده ادعا نمی‌شود و بررسی خود digest پیش از استقرار در قرارداد نهایی لازم است.
- بررسی حفاظت شاخهٔ `dev` با API به علت محدودیت مجوز integration با 403 ناموفق بود؛ وضعیت حفاظت، مجوز package و دسترسی pull سرور تأیید نشده‌اند.

## تصمیم و پیگیری

- دستیار زیرساخت باید قرارداد امن deploy، صف، منابع، migration/backup/rollback، پیکربندی و پذیرش gate را با این نیازها تطبیق دهد. نسخهٔ هماهنگ‌شدهٔ طرح برای تأیید یک‌جای مالک ارائه شود؛ تا آن زمان اجرای اولیه روی VPS و تغییر DNS ممنوع است.
- تصمیم قبلی اعتبار یک‌ساعته و برداشت محدودیت معماری تک‌دستگاه با تصمیم‌های جدید جایگزین شده‌اند. مجوز `read:org` قبلی فقط برای App محلی آزمایشی بود و به App نهایی یا استقرار تعمیم داده نمی‌شود؛ نگهداری یا لغو grant محلی همچنان تصمیم مالک است.
- این گزارش جای Vault نیست؛ ثبت چهار تصمیم، مسئولیت‌ها و طرح تأییدشده در نشست جداگانهٔ Vault پیگیری شود. هیچ تغییری در Vault در این نشست انجام نشده است.
