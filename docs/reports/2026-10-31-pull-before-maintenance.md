# Pull پیش از maintenance

- **تاریخ و مبنا:** ۲۰۲۶-۱۰-۳۱، [PR #13](https://github.com/feerozmandi/xennic-website/pull/13). این مرحله زنجیرهٔ استقرار را کامل نکرده است؛ SSH و deploy غیرفعال‌اند و VPS/DNS تغییر نکردند.
- **تغییر:** کنترل‌کننده پس از بررسی اولیه و پیش از blocked/backup، pull را فراخوانی و پس از آن current را دوباره بررسی می‌کند. شکست pull در آزمون واحد به journal یا backup نمی‌رسد. `scripts/preview-pull-image.py` فقط manifest مجاز و token در stdin می‌پذیرد و Docker pull با digest ثابت GHCR و معماری `linux/amd64` و بررسی شناسه/RepoDigest را اجرا می‌کند؛ خودش شاهد مستقل موفقیت انتشار نیست.
- **نصب و آزمون:** installer فعلی pull را در کنار helperهای backup/SFTP نصب می‌کند، نه تمام helperهای کنترل‌کننده. آزمون ورودی نامعتبر همان فایل نصب‌شده در PR و آزمون واقعی GHCR همان helper فقط در job انتشار push به `dev` اضافه شده است؛ token آن فقط `GITHUB_TOKEN` همان job است، نه secret عملیاتی در PR. تا اجرای موفق آن job، pull جدید آزمون واقعی GHCR محسوب نمی‌شود. قبل از این تغییر، [CI 41217374803](https://github.com/feerozmandi/xennic-website/actions/runs/41217374803) backup/SFTP نصب‌شده را با داده و release مصنوعی آزمود. تست rollback قبلی از adapter آزمایشی استفاده می‌کند و زنجیرهٔ جدید محسوب نمی‌شود.
- **مانع مشخص:** `scripts/preview-deploy-backend.py` در `PHASES` به helperهای ثابت `release-check`, `current-check`, `migrate`, `activate`, `health`, `rollback` نیاز دارد ولی installer این فایل‌های عملیاتی را ارائه نمی‌کند؛ `FixedRunner.verify_helpers` عمداً پیش از تغییر fail-closed می‌شود. راه‌حل: تکمیل همین helperها و installer، دریافت شاهد run موفق و artifact آن از GitHub، محدودکردن migration به سازگاری بازبینی‌شده، سپس اجرای موفق و شکست پس از activation با همان فایل‌های نصب‌شده در CI. در PR بدون انتشار `dev`، شاهد واقعی GHCR برای commit جدید وجود ندارد؛ شاهد قبلی به آن تعمیم نمی‌یابد.
- **Vault:** مرجع جدا فقط‌خواندنی ماند؛ مقصد backup و تنظیمات مالک در زمان مناسب جداگانه پیگیری شوند. هیچ secret عملیاتی دریافت یا استفاده نشد.
